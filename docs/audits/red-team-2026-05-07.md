### C-006 — closed (переквалификация)

**Изначальная формулировка:** "security-reviewer vs ccip-security ambiguity".

**Уточнение:** это не ambiguity, а два разных агента с разделёнными ролями:

| Агент | Роль | Tools | Когда вызывается |
|-------|------|-------|------------------|
| `ccip-security` | Security Engineer (full-write) | Read, Write, Edit, Glob, Grep, Bash | RBAC-аудит, threat model, OWASP, pre-launch review, secret management |
| `security-reviewer` | Блокирующий co-agent (read-only) | Read, Glob, Grep | Параллельный review при изменениях JWT/RBAC/RLS/multi-tenancy/AuditLog с severity-вердиктом |

**Что нужно зафиксировать:** правила выбора в CLAUDE.md (сейчас `SECURITY → security-reviewer` без упоминания `ccip-security`).

**Owner:** ccip-architect (часть T2).

```json

  "session_id": "",
```

## 6. Resolutions (T2 — ccip-architect, 2026-05-07)

### C-006 — CLAUDE.md routing fix

**Решение:** `SECURITY` в Intent→Agent table переключён с `security-reviewer` на `ccip-security` (primary, full-write). В Risk Rules добавлено явное правило: `security-reviewer` — автоматический co-agent при risk:HIGH, не первичный агент; ccip-security — primary для целенаправленных SECURITY-задач.

**Обоснование:** разделение на два intent-кода (SECURITY-REVIEW / SECURITY-AUDIT) добавляет cognitive load вызывающему агенту без выгоды. Достаточно одного правила в Risk Rules — кому и когда.

**Файл:** `CLAUDE.md`

---

### R-001 — session-state.json как источник artifacts

**Решение:** вариант (c) с уточнением. Шаг 1 алгоритма security-reviewer заменён: источник — `artifacts` из `handoff_notes` вызывающего агента (контекст invocation), fallback — явный запрос у пользователя. Ссылка на `session-state.json` удалена.

**Обоснование:** session-state — harness concern. Агент уже получает контекст через handoff_notes от primary agent; принудительное чтение файла на пустом skeleton давало silent fail (empty artifacts → APPROVED без реальной проверки).

**Файл:** `.claude/agents/security-reviewer.md`

---

### R-002 — BLOCK без DAG enforcement

**Решение:** вариант (b). Description в frontmatter и Блокирующий протокол переформулированы: BLOCK-вердикт означает что primary agent не должен коммитить без явного подтверждения пользователя. Добавлено явное указание: "organizational protocol, не машинный enforcement".

**Обоснование:** декларация "DAG не может пометить шаг как done" вводила в заблуждение — DAG executor не существует и не планируется для single-developer проекта. Честная формулировка лучше ложного обещания.

**Файл:** `.claude/agents/security-reviewer.md`

---

### C-004 (разблокирование) — каноничный путь SLA worker

**Решение:** `apps/api/src/modules/dispute-sla/` (вариант a). BullMQ Processor-класс размещается внутри модуля рядом с сервисом. Разделение процессов (api vs worker) осуществляется через `WORKER_ROLE` env var на уровне `main.ts`, не через файловую структуру.

**Обоснование:** соответствует сложившемуся паттерну — `period/`, `analytics/`, `zero-report/` — всё живёт в `modules/<name>/`. Вариант (b) с отдельным `workers/` каталогом создаёт риск circular dependency и противоречит паттерну монорепо. Phantom path `apps/api/src/sla-scheduler/` в delivery docs подлежит замене на `apps/api/src/modules/dispute-sla/` (owner: ccip-doc-writer, T3).

**Файлы к исправлению (T3):**
- `docs/delivery_plan_v1_0.md:321`
- `docs/delivery/phase-4-7-backend-modules.md:81`
