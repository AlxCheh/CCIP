# §XII Strategic Recommendations — Sequenced Roadmap

> **Тип:** roadmap-спина (последовательность + зависимости + entry/exit-критерии волн). **НЕ** bite-sized TDD-план — детализация каждой волны делается отдельным документом непосредственно перед её стартом.
> **Базис:** `docs/audits/2026-06-12-capability-assessment.md` §XII; сверено с реальным кодом `.claude/runtime/` + `tools/audit/` на HEAD `b9dcb27`.

**Goal:** Реализовать все 9 рекомендаций §XII в порядке, продиктованном фактическими зависимостями механизмов, а не порядком перечисления в отчёте.

**Принцип отчёта (неотменяемый):** повышать метку возможности ([НЕДОК.]→[ЧАСТ.]→[ПОДТВ.]) можно **только новым подтверждающим механизмом + тестом**, не переписыванием формулировки. Каждая волна закрывается обновлением соответствующих строк capability-assessment + журнала.

## 2. Граф зависимостей

```
Независимые (нет блокеров):
  #5 token-attribution ── поверх events.jsonl
  #1 auto-remediation  ── поверх audit-детекторов
  #4 fail-closed flag  ── изолированно на state-lock.js
  #3 persisted DAG     ── изолированно на execute-dag.js

Зависят от накопленных данных / методики:
  #2 signal→enforced   ── §XII.2 явно «после накопления данных» → после запуска #5
  #6 failures/agent    ── ИНСТАНС методики #2 + failure-телеметрия → после #2

Зависят от enforcement:
  #7 expand agents     ── безопасно только при #6 (ограничение runaway / bad-routing)
  #9 self-governed     ── капстоун: #1 (словарь авто-коррекций) + #6 + detect→react

Ортогонально (путь к Mission-Critical):
  #8 formal model      ── валидирует block-инварианты ПОСЛЕ стабилизации их набора (#2/#6)
```

**Критический нюанс фронт-лоадинга #5:** #2 буквально требует «после накопления данных». Телеметрию (#5) надо запустить раньше всех enforcement-промоушенов, чтобы данные копились, пока идёт остальная Волна 1. #5 первым — не по важности, а по времени накопления.

## 3. Последовательность волн

### Волна 1 — независимые основания + enabler данных
**Состав:** #5 (первым), #1, #4, #3.
**Почему вместе:** взаимно независимы, low-risk, high-ROI, разблокируют поздние волны.
**Внутренний порядок:** #5 → #1 → {#4, #3 в любом порядке}.
- #5 первым: запускает накопление token-данных для Волны 2.
- #1 второй: Max-ROI + создаёт первый класс «авто-коррекции», который обобщает #9.
- #4, #3: изолированные, без зависимостей между собой.

**Entry-критерий:** нет (старт программы).
**Exit-критерий волны:**
- #5: token-оценка на `events.jsonl` тестируется; capability-строка «token-attribution / main-agent token-blindness» в §I, §VII, §XI обновлена с доказательством.
- #1: auto-fix хотя бы одного детерминированного класса (anchor **или** dead-ref) с тестом; §III «Tooling» / §XII.1 помечены реализованными.
- #4: флаг fail-closed с тестом обоих режимов (open/closed); §I, §V «Наблюдаемый fail-open» обновлены.
- #3: журнал DAG переживает рестарт сессии, resume из журнала с тестом; §II «Долгоживущие workflow 45%» переоценена.
- Канонический раннер зелёный (≥362), audit-suite зелёный (≥22), live re-cert строки в журнале capability-assessment.

### Волна 2 — промоушены enforcement
**Состав:** #2, затем #6.
**Entry-критерий:** #5 в проде ≥ N сессий с накопленными token/failure-данными (точное N определяется при детализации волны по объёму данных, нужному для оценки FPR); #1 даёт прецедент детерминированного авто-действия.
**Внутренний порядок:** #2 → #6.
- #2 первым: выбирает 1-2 зрелых сигнала с измеренным FPR→0, переводит в enforced по методике `contract-exempt`/`CCIP_GATE_ENFORCE`. Доказывает методику повторно.
- #6 вторым: применяет ту же методику к per-agent failure-счётчику (новый counter поверх `failure-detectors.js`) → авто-switch на backup. Переводит routing-конвенцию CLAUDE.md §18 (`agent fails >= 2 → switch to backup`) из [НЕДОК.] в [ПОДТВ.].

**Exit-критерий волны:**
- #2: ≥1 сигнал enforced с FPR-обоснованием и тестом; строки §V, Dependency Trust Matrix §IV обновлены.
- #6: per-agent counter + enforced switch с тестом; CLAUDE.md §18 строка `agent fails >= 2` помечена machine-enforced; §II «Динамическая маршрутизация 30%», §IV «Feedback↔Routing» переоценены.
- security-reviewer co-agent привлечён, если затронуты RBAC/AuditLog поверхности (вероятно нет, но проверить на детализации).

### Волна 3 — новые классы возможностей
**Состав:** #7, затем #9.
**Entry-критерий:** #6 enforced (ограничивает runaway при росте числа агентов); #1 реализован (словарь авто-коррекций для #9).
**Внутренний порядок:** #7 → #9.
- #7: расширение лимита агентов (>3) с per-agent изоляцией состояния поверх атомарного RMW (ADR-019). Безопасно только при #6.
- #9: капстоун — связать `governance-reactor.js` detect→react с авто-корректирующими директивами для воспроизводимых классов аномалий (опора на #1).

**Exit-критерий волны:**
- #7: расширенный лимит с per-agent state-изоляцией и тестом конкурентности; §VI «Enterprise Orchestrator / Distributed Agent Platform», §VIII.2 переоценены.
- #9: ≥1 класс аномалии с авто-коррекцией end-to-end (detect→react→fix) и тестом; §VI «Self-Governed Runtime 70%», §V обновлены.

### Волна 4 — путь к Mission-Critical
**Состав:** #8.
**Entry-критерий:** набор block-инвариантов стабилизирован после Волны 2 (#2/#6 добавляют/промоутят инварианты — моделировать движущуюся цель бессмысленно).
**Exit-критерий волны:**
- #8: формальная модель 3-4 block-инвариантов (TLA+ **или** Alloy) с проверенными свойствами; §I «нет формальной верификации [ОТСУТ.]», §IX «Mission-Critical Runtime», §XIII «путь к Mission-Critical» обновлены.

## 5. Процессные инварианты программы (каждая волна)

1. **TDD** с serial-guard (CLAUDE.md §17, M-1): тест-семантика, не имена классов.
2. **Commit-per-finding / per-механизм**, частые коммиты.
3. **Live execution-based ре-сертификация**: после каждой волны — канонический раннер + audit-suite зелёные, строки в журнале capability-assessment обновлены **только** с доказательством.
4. **security-reviewer co-agent** обязателен, если волна трогает JWT/RBAC/RLS/multi-tenancy/GpToken/AuditLog (INV-SECURITY-COAGENT) — проверять на детализации каждой волны.
5. **ADR-immutability**: новые решения (особенно #4 fail-closed, #6 enforce, #7 лимит, #8 формальная модель) фиксируются новым ADR, не правкой accepted-ADR.
6. **Design-question-first** на governance-развилках: реврейминг фактами + AskUserQuestion, до кода.

## 6. Открытые вопросы (решить при детализации волн)

- **#5:** какой источник оценки токенов доступен «через доступный канал» — эвристика bytes→tokens по `events.jsonl`, или внешний counting-API? Определяет точность и метку ([ЧАСТ.] vs [ПОДТВ.]).
- **#2:** какой именно сигнал(ы) первым кандидатом на enforce — зависит от накопленных FPR-данных Волны 1. Нельзя зафиксировать до данных.
- **#2/#6:** точное N сессий накопления данных перед оценкой FPR.
- **#8:** TLA+ vs Alloy — какие 3-4 инварианта моделируем (кандидаты: INV-STATE-CONTRACT, INV-AGENT-BUDGET, INV-SECURITY-COAGENT, cross-process lock ADR-019).
